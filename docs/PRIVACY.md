## The placeholder guard

`scripts/check_privacy_placeholders.mjs` fails while any placeholder (`<mark class="privacy-confirm" data-confirm="P…">`) remains on the page, listing each ID. It fails closed: a placeholder element counts whatever its attribute quoting (double, single or none), and so does any other mention of `privacy-confirm` or `data-confirm`, or any "[To confirm" or "[To decide" text that has lost its wrapper (reported as `?`). Comments and `<style>` blocks are ignored. It runs at the end of `npm run check` and first in `npm run deploy` and `npm run deploy:staging`; the GitHub deploy workflow (`.github/workflows/deploy.yml`) deploys through `npm run deploy`. A bare `npx wrangler deploy` bypasses it, as it already bypasses asset stamping; never deploy that way. `portal/test/privacy-placeholders.test.mjs` tests the detection, the command's exit codes on fixture pages, and that `check`, `deploy` and `deploy:staging` all run it (the deploys first). The page has none today; keep the guard for any future draft.

## Where it lives

- **Scope (12 October 2026):** `/privacy` covers the website and the OPAX app for iPhone, iPad and Android. Only the two opening scope statements changed; the App Store label, other policy wording and section anchors remain unchanged. The policy does not list account types, so store reviewer accounts are not added.
- **The page** is the `/privacy` panel in `portal/public/index.html` (`#panel-privacy`), routed in `app.js`, described in `STATIC_PAGES` and the sitemap in `src/index.ts`, and linked from the About menu, the mobile drawer and the footers of `index.html`, `home.html` and `community.html`. It is the privacy policy URL for the App Store listing and the app's Account and about screen: `https://opax.com.au/privacy`. `/support` (`#panel-support`) is the App Store support URL.
- **Served whole by the Worker.** `/privacy` and `/support` are in `SERVER_PANELS` (`src/seo-content.ts`). For them the Worker reads its own shell (`index.html`), copies the panel's inner markup with `panelPrerender()` and serves it as `#prerender` (`data-panel-copy`, class `policy-page`), so the full policy text is in the HTML for App Review, crawlers and readers without scripts, from the same markup the app's panel uses. The association caveat is not added to these two pages. Once the app boots, `.spa-ready #prerender` hides the copy and `spa-shell.js` (generated by `scripts/build_spa_shell.mjs`) strips the copy's ids, so the panel's anchors stay unique. Both pages use the `.policy-page` styles. Tests: `test/store-pages.test.mjs` and the `/privacy and /support are served whole` case in `test/seo-render.test.mjs`.
- **The app section** (`#privacy-app`, list `#privacy-app-data`) states the app's App Store privacy label and its Google Play Data safety answers: nine types, in the order of [IOS-STORE.md](IOS-STORE.md) section 4.1 (the seven of `release/1.0/app-privacy.json` on the store branch, `release/store-1.0`, then Device ID and Crash Data), each with its Play name from [ANDROID-STORE.md](ANDROID-STORE.md), "Data safety". Change the page, the saved App Store Connect answers and the saved Play Console answers together; `test/store-pages.test.mjs` pins the list.
- **`/terms` and `/security`** (14 November 2026) are built the same way: `#panel-terms` and `#panel-security` in `index.html`, in `STATIC_PAGES`, `SERVER_PANELS`, the crawl catalog's static paths and the footers beside Privacy. `/terms` covers the website, the app and the MCP service. `/.well-known/security.txt` is a Worker route (`SECURITY_TXT` in `src/index.ts`) naming the same two contacts as `/security`; renew its `Expires` before 14 November 2027 (a test in `test/seo-render.test.mjs` fails 30 days ahead). Tests: `test/terms-security.test.mjs` and `test/seo-render.test.mjs`.
- **Section anchors** are stable and other surfaces link to them: `#voice` (the voice panel and the app's consent screen), `#voice-allowance`, `#privacy-questions`, `#privacy-deletion`, `#privacy-contact`, `#privacy-app`; on `/support`, `#support-contact`, `#support-report`, `#support-answers`, `#support-account`, `#support-delete`. Keep these IDs if the page is rewritten.
- **`/support?record=<path>`** names a reported record, by its catalog title, and puts its path in the public GitHub issue only when the path is exactly the page of a record OPAX publishes. `npm run build:search` writes a path index beside the catalog shards (`search-catalog/<version>/paths-<n>.json`, 256 files keyed by an FNV-1a hash of the canonical path). Each path takes the title of the record that owns its page: the grant-recipient record, or the record whose kind matches the route. A person's page is indexed under both its addresses, the name the catalog links and the slug the site settles on (`/subject/person/tony-abbott`, from the Worker's own `src/person-slug.ts`), with one title; a twin spelling's slug names the fuller entry, as the router does. `/support` loads `public/record-paths.js` and the one index file lazily, only when a `record` is given. The path is decoded once and refused with dot segments or encoded separators before any lookup. A miss, a failed fetch or being offline leaves the report general, with no path in it.
- **The old community view** `/community?view=privacy` hands over to `/privacy`, keeping any fragment, before any account request. Sign-in emails already sent and the web voice panel (`portal/voice/client.js`, `/community?view=privacy#voice`) still link there, so keep the hand-over.

## Keep the page true

The page states facts about the live system. Change it in the same commit as any change to:

- what a table in `portal/migrations/` stores about a member, or what account deletion removes or keeps (`src/community-deletion.ts`);
- rate limits keyed to IP addresses (`wrangler.jsonc` `ratelimits`, `limit()` callers in `src/`), logging (`observability`) or anything that forwards a client address (`src/posthog.ts`);
- analytics (`portal/analytics/`, `public/gtm.js`, [ANALYTICS.md](ANALYTICS.md)), browser storage keys in `public/*.js`, or chat sync to the account;
- which searches reach Progress or a model (`apiUnifiedSearch()`, `apiSearchSummary()`, the Ask routes), or a provider that receives reader data: Progress Agentic RAG, the OpenRouter model pins, ElevenLabs, Google, PostHog, OpenStreetMap tiles, Cloudflare Email Sending;
- the voice allowance, monthly budget, concurrency, reservation accounting or provider settings ([VOICE-ASSISTANT.md](VOICE-ASSISTANT.md));
- what the iPhone, iPad and Android app stores, sends or asks permission for, its App Store privacy label (`release/1.0/app-privacy.json`, `mobile/voice-production-policy.json`) or its Google Play Data safety answers (`docs/ANDROID-STORE.md`).

Then update the "Last updated" date. The page's history is this repository's history.

What the code guarantees: `portal/src/openrouter.ts` is the only module that builds an OpenRouter client, and it sets the two fields after any configured preference, so no variable can remove them. `portal/test/openrouter-privacy.test.mjs` reads the request bodies the real client produces for every configuration in `wrangler.jsonc` and fails if either field is missing, or if any other Worker or enrich module imports the client or names the OpenRouter API host. If no pinned provider satisfies the fields, OpenRouter refuses the request rather than routing it elsewhere, and Ask fails closed (hub ruling, 16 November 2026): the reader gets an error to retry, and no other generation request is built for that question, neither the older planner nor the older engine (both generate on the second row's route) nor a further OpenRouter call. **What OPAX's code sends to a model on Progress's side.** At index time: text is embedded with Progress's own `multilingual-2024-05-06` (`portal/public/corpus.json`, `MIGRATION-ARAG.md`); no third-party model is called unless a data-augmentation task is run (`scripts/arag_enrich.py`, `scripts/arag_bill_text_labeler.py`, which send text to OpenRouter, `deepseek/deepseek-v4-flash`, unpinned), and `scripts/publish_collected_bill_texts.py` refuses to publish while any task is enabled or a generative summary model is configured. The knowledge box's `summary_model` is recorded two ways in the repository (`scripts/arag_byok_openrouter.py` sets it to the OpenRouter slot; `publish_collected_bill_texts.py` describes a legacy value that generates nothing); the live value was not read. At query time: `/find` uses Progress's embedding and its `predict` reranker (`portal/src/index.ts`, `research-loop.ts`); query rephrasing is off where OPAX sets it; and every `/ask` with generation sends the question and the retrieved passages to OpenRouter's `@preset/opax-pro`, pinned to DeepSeek (the second row of the table above). So any text stored in the knowledge box can reach that provider whenever it is retrieved for one of those features. Separately, passages the research loop retrieves go from OPAX's Worker to OpenRouter under the enforced fields. Settings that control this are per knowledge box (`/configuration`: `generative_model`, `summary_model`, `user_keys.openai_compat`; `semantic_model` and `anonymization_model` at creation) and `generative_model` per request.

**How long a delete takes: not measured.** The delete is one synchronous `DELETE /slug/{slug}` (`parli/arag.py` `delete_resource_by_slug`; `parli/ingest/kb_text_patch.py` treats a 404 as done). No committed log or runbook records how long a deleted resource stays retrievable, and no code checks.
