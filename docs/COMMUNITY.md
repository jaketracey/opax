# Opax community

## Product contract

The public record stays open. An email account enables private or shared reading lists, public profiles and source-led discussions. The read-only MCP tools need no account; an account gives a member their own limit. All community features are available to members without payment.

## Implementation

- `/community` serves responsive account, discussion, reading-list and connected-tool views. Shared desktop/mobile navigation links to the community.
- `/api/community/*` owns isolated D1 community data. Staging never proxies account requests to production.
- Magic links expire after 15 minutes, are stored only as hashes and are consumed atomically after an explicit POST. Tokens travel in URL fragments, which the browser removes immediately. Email scanners cannot consume them by fetching the link.
- Native code sign-in uses the same proof and session as the web; see the code flow below. Only native requests supersede earlier unused iOS proofs for the same normalized email. Web links remain independently usable until consumed or expired, including when a later web email fails to send.
- Sessions use hashed random tokens and a Secure, HttpOnly, SameSite=Lax `__Host-` cookie. Account mutations require the configured origin. Login and content creation are rate-limited.
- Reading lists start private. Owners control sharing and deletion; public profiles omit email. Saved records use Opax's `/doc/` paths.
- Saved conversations (13 September 2026): the chat keeps every conversation in the browser's localStorage (`opax-chats`, twenty newest, trimmed sources) and mirrors a signed-in member's to `member_chats` (migration 0006) through `GET/PUT/DELETE /api/community/chats[/:id]` - one owner per row, private, the reader's `updated` clock deciding between devices (an older write is acknowledged as `stale`). Fifty per member; a body up to 600 KB and eighty turns. Nothing anonymous is stored server-side.
- Members can report discussion content; moderators can review reports and hide content. Assign moderation ownership before opening discussions.
- MCP is stateless HTTP POST at `/mcp`. The access layer is `portal/src/mcp-access.ts`; three kinds of caller reach the same read-only public-record tools:
  - **No account** (built 14 November 2026): a request with no `Authorization` header is served. No personal data is read or stored for it. Limits per minute, each counted in `community_limits` under a hashed key:
    - one client, 60 (`MCP_ANON_PER_CLIENT_MINUTE`) as a token bucket with up to 30 at once, because assistants fire several tool calls in parallel. A client is its `Mcp-Session-Id` at its address; OPAX issues one at `initialize` (a random value, never stored or looked up). Without a session it is the `User-Agent` at its address. `initialize`, `tools/list` and `ping` do not use this allowance. The session id is the caller's own word, so this is fairness between honest clients; the address ceiling is the real stop.
    - one address, a ceiling of 300 (`MCP_ANON_PER_IP_MINUTE`). An address is an IPv4 address or an IPv6 /64. The Workers rate limiter `MCP_ANON_LIMITER` (300 a minute per address) refuses a flood before any database write and fails open.
    - addresses many people share, a ceiling of 1,500 (`MCP_ANON_SHARED_IP_MINUTE`) and no per-client allowance without a session. These are Anthropic's and OpenAI's published server ranges (`portal/src/mcp-shared-egress.ts`; refresh the OpenAI list from `https://openai.com/chatgpt-connectors.json`) plus any in `MCP_ANON_SHARED_RANGES`. The daily watchdog warns when OpenAI publishes ranges the file lacks; `python3 scripts/refresh_mcp_egress.py --write` rewrites it. Claude and ChatGPT call from those servers, not from each person's address, so one person's allowance would throttle everyone.
    - everyone together, 3,000 (`MCP_ANON_GLOBAL_MINUTE`), counted separately for the shared addresses and for everyone else, so neither crowd can shut the other out. The checks run in order (address, client, everyone): a request refused for its address or client uses none of the wider allowance.
    Over a limit the answer is HTTP 429 with `Retry-After` (the exact wait for a client's bucket, the rest of the minute for a ceiling) and a JSON-RPC error (code -32029, `data.retry_after_seconds`) whose message names the limit and the account option. The first no-account request of each hour clears limit rows a day past their window. `/mcp` is outside `network-block.ts`, so no network is refused there.
  - **Daily spend guard (automatic):** counts per UTC day in `community_limits`, numbers only, in two pools: the shared addresses above ("shared") and everyone else ("direct"), so neither crowd can pause the other. When a pool reaches either of its caps the tier pauses itself for that pool's callers until the day ends: `/mcp` answers 401 as with the kill switch off, members and the other pool are unaffected, a paused pool writes nothing, one `mcp_anon_daily_cap` line is logged, `/api/mcp/status` lists the pool in `paused_today` (for example `["direct:progress"]`), and the daily watchdog fails.
    - **Progress queries**, `MCP_ANON_DAILY_PROGRESS_SHARED` and `MCP_ANON_DAILY_PROGRESS_DIRECT` (250 each, 500 a day in all until the price per query is measured). Each query to the Progress knowledge base is counted as it is made, not each tool call: every request carries a meter (`progressMeter` in `mcp-access.ts`) that `kbFetch` and the corpus reader call before each query. A search can make two (its main query and the keyword retry it starts when the main one is slow or fails, `search-find.ts`); a cached answer makes none. A query refused part-way through a tool makes the whole request a 429 with `Retry-After` to midnight UTC, never a tool result.
    - **Requests**, `MCP_ANON_DAILY_REQUESTS_SHARED` and `MCP_ANON_DAILY_REQUESTS_DIRECT` (100,000 each): every no-account request.
    - **One network's allowance** (direct pool only): `MCP_ANON_DAILY_PROGRESS_NETWORK` (150 queries) and `MCP_ANON_DAILY_REQUESTS_NETWORK` (20,000 requests) per IPv4 address or IPv6 /48, under hashed keys. Past either, that network alone gets 429 with `Retry-After` to midnight UTC and the account option, and one `mcp_anon_network_cap` line is logged (no address). Its refused requests use none of the pool, so one network, however many session ids it invents, cannot pause the tier for anyone else. The shared pool has no per-network allowance: one of those addresses carries many people.

    Worst case for no-account traffic in a day, by backend:

    | Backend | What reaches it | Worst case a day |
    | --- | --- | --- |
    | Progress knowledge base | record search and reading (`search_records`, `read_record`, and the tools and registers that use the corpus reader, such as `hansard_search` and `member_profile`) | 500 queries. The price per query is not yet measured, so no dollar figure is given. Divide a daily budget by the measured price to resize the two pool caps. |
    | Language models (OpenRouter), Workers AI | nothing: no MCP tool calls a model | none |
    | Cloudflare Workers requests | every request | 200,000 served requests |
    | Cloudflare D1 | limit and count rows, about six written per served request, two more per Progress query | about 1.2 million rows |

    Requests refused while paused, for a spent network, or by the Workers limiter, cost a Worker invocation and at most one database read each.
  - **Measuring queries per tool:** on staging (`MCP_PROGRESS_REPORT` `"true"`) every `/mcp` response carries `x-opax-progress: find=<n>, hedge=<n>, other=<n>` (main searches, keyword retries, other knowledge-base reads), and a caller may send `x-opax-progress-budget: <n>` to refuse its own request past n queries. A caller can only lower its budget. Production ignores both. `portal/scripts/mcp-progress-probe.mjs` uses them to measure each tool: it prints its plan by default and runs only with `--run`, against staging only, at one request a second, stopping at 50 tool calls or 100 queries counted. Staging runs the MCP tools' searches and record reads in its own Worker with its own reader key (not through `STAGING_API`), so its counts match production's. Running the probe uses Progress queries: ask first.
  - **Kill switch:** `MCP_ANON_ENABLED` must be exactly `"true"` for the no-account tier. It is `"false"` for production in `portal/wrangler.jsonc` until the tool quality gates pass; the tier, the privacy wording and the `/mcp` page go live in one deploy. Any other value returns `/mcp` to members only (HTTP 401 with the sign-in pointer); keys and connected clients keep working. Change it in `portal/wrangler.jsonc` and deploy. It is an emergency lever: a connector listed as needing no sign-in fails its directory health checks while the switch is off, so tell the directories (Anthropic: mcp-review@anthropic.com; OpenAI: platform support) if it stays off for long.
  - **Volume alert:** each no-account request adds to an hourly count (`mcp-anon-hour:<hour>` in `community_limits`, a count only). When an hour passes `MCP_ANON_ALERT_HOURLY` (20,000) the Worker writes one `mcp_anon_volume` warning to Workers observability, the same sink Ask monitoring uses. `GET /api/mcp/status` returns `{anonymous, volume, hours_over}`; `volume` is `high` when three hours in a row passed the line in the last day. The daily refresh watchdog (`scripts/refresh_watchdog.py`) reads it and fails, which emails the repository owner.
  - **Member key:** a personal bearer token (`opax_…`). Tokens are stored hashed, expire after 90 days and can be revoked. A member can have three active tokens. Limits: 60 tool calls a minute for one session (`Mcp-Session-Id`) with up to 30 at once, and a ceiling of 300 a minute across the member's sessions. Connecting and listing tools are counted apart (300 a minute), so many short sessions do not use up the allowance. Before 14 November 2026 the limit was a flat 60 requests a minute per member, which refused parallel sessions.
  - **Sign in to connect** (OAuth 2.1, `portal/src/community-oauth.ts`, migration 0019): for clients that can sign in. `/mcp/member` is the same server but always answers 401 without a token, because clients only start sign-in on a 401. Details are in the section below.
- A presented token that is wrong, expired or removed is answered 401, never served as a no-account request. `/mcp` sends credential-free CORS headers (`Access-Control-Allow-Origin: *`): no caller is identified by a cookie, so a browser page gains nothing a direct request would not have.
- A plain GET of `/mcp` with no token gets the setup page `portal/public/mcp.html`. An MCP client's GET asks for `text/event-stream` and is answered 405.
- `tools/list` holds 16 read-only tools and stays under 30 KB, because every client keeps it in context on every turn:
  - record search and reading: `search_records` (with a `grant` kind and a `page` argument), `read_record`, `find_connections`, `corpus_coverage`, `read_grant_recipient`, `read_grant_program`;
  - members, votes, bills, money, interests and Hansard: `member_profile`, `division_votes`, `member_voting_record`, `bill_search`, `bill_detail`, `money_receipts`, `member_interests`, `hansard_search`. Each returns `items`, `total`, `next_cursor`, `notes` and `url`, takes `detail` (`concise` or `full`) and pages with an opaque `cursor`;
  - the specialised registers (grants, contracts, pay, expenses, annual reports, integrity reports, royal commissions, counts and others): `query_register({register, arguments})`. Its `register` parameter lists each register with its main arguments and their allowed values (`REGISTER_ARGS` in `mcp-listing.ts`, checked against each schema by a test), so a client can call it without a guide turn. `register_guide({register})` returns one register's description, full arguments and examples, and a wrong call returns the same guide.
- Every tool declares an `outputSchema` and returns `structuredContent` with the same JSON as text. Every result carries an absolute OPAX link to cite (`url`, `opax_url` or per-row links). Tool definitions and listing text live in `portal/src/tools/` (`mcp-listing.ts` holds the names, titles and descriptions the MCP shows).
- Bad arguments come back as a tool result with `isError: true` that says which argument was wrong and gives an example call, so a model can correct itself. They are not JSON-RPC protocol errors.
- Earlier tool names still answer a `tools/call` until the next release but are no longer listed: every registry tool by its own name, `paid_answer` (now the `pay_calculator` register) and `ranked_money` (now `money_rankings`), and the tools the newer ones replace (`member_divisions`, `member_votes`, `money_totals`, `party_receipts`, `sponsored_bills`, `find_people`, `person_overview`, `person_quotes`, `find_quotes`, `search`, `read_passage`).
- No tool reads account data. They read published exports, the published tables and the search index only, so results do not depend on who is asking.
- Grant search hits point at the file to open next. A recipient row carries `grant_recipient: {jurisdiction, id}` for `read_grant_recipient`; a program row (catalog slug `grant-program-<jur>-<key>`, title ending in "(grant program)") carries `grant_program: {jurisdiction, id}` for `read_grant_program`.
- Recipient citations use `/money/grants/<jurisdiction>/recipient/<encoded-id>` for standalone pages. Legacy `/money/grants?jur=...&open=...` links remain readable, and MCP search recognizes both forms.
- `read_grant_recipient` adds `program_lookup` entries for its top program labels. Each entry includes the recipient value and catalog `candidates` with `{jurisdiction, id, name, opax_url}`. These are label matches; verify membership in the program's grants. An empty candidate list means no matching exported program, not that no program exists.
- `read_grant_program({jurisdiction: "federal" | "qld", id})` resolves a canonical catalog ID, file key, or unique exact program label against `/graph/grants.<jur>.json`. It uses the catalog's file key, including exporter collision suffixes and truncation. Multiple programs with the same label return an error with candidates; an unknown program returns `{"error":"not found"}`. Only exported catalog programs are available.
- Both grant readers include `field_guide`, `coverage`, `dataset_source_url`, `grants_total` and `grants_listed`. Recipient agencies/programs/electorates and program top recipients may be partial summaries. Queensland values are annual expenditure lines, including grants, service agreements and other assistance; an agreement can recur in several years. Federal values are published award values, not evidence of payments received. Do not combine counts as unique grants or totals as payments received.
- A known GrantConnect GUID yields a row `source_url` with `source_kind: "original_record"`. Queensland rows without an individual URL instead link to the source dataset with `source_kind: "dataset"`. Missing individual record URLs are explicit in `original_source_status`. Dataset provenance does not verify an individual record, and external link availability is not guaranteed.
- A tool result is capped at 80 KB (about 25,000 tokens). The grant readers list the 10 largest grants by default and as many as fit with `detail: "full"`; totals and metadata are preserved and `truncated: true` is set whenever the list is incomplete. Recipient asset omissions also set `truncated`. If metadata alone exceeds the cap, the tool returns an error with the OPAX URL. A speech too long for one response is read in parts with `hansard_search` (`record_id`).

  Example: use the candidate returned for Community Development Grants:

  ```json
  {"name": "read_grant_program", "arguments": {"jurisdiction": "federal", "id": "GO3141"}}
  ```

  The exact label `"Community Development Grants"` also resolves when unique. The response includes the canonical `id: "GO3141"`, `key: "go3141"` and `opax_url: "https://opax.com.au/money/grants?jur=federal&program=GO3141"` alongside current program data and coverage notes.

## Native code sign-in (W1 to W3, live since 3 October 2026)

`POST /api/community/auth/request` accepts `{email, client:"ios"}`. Omitting `client` keeps the web email and response unchanged. Native requests receive `{sent:true, message, challenge_id}` for both existing and new accounts. The challenge is 32 cryptographically random bytes encoded as 43 URL-safe characters and bound in the proof row to the normalized email and `client:"ios"`. The response carries no code or link token.

The native email includes the existing `/community?view=signin#token=…` link and an eight-digit app code, including possible leading zeroes. Its copy says never to share the code and explains that the link signs in through the browser, not the app, and consumes the code too. Rejection sampling over `crypto.getRandomValues` makes every code equally likely. One proof holds the SHA-256 link hash, the challenge and an HMAC-SHA-256 of the code bound to that challenge. The code is never stored in clear or as an unkeyed hash. The proof expires after 15 minutes. The new proof is inserted first. Only after the email is accepted are older native proofs for that email superseded; supersession also sets their `expires_at` to the current time, so the existing link-consume SQL refuses them. Email-delivery failure deletes the newly created proof and leaves earlier codes and links working. The web and native share the existing `login-ip:` and `login-email:` counters: 15 per fixed hour per IP and 5 per fixed hour per email.

`POST /api/community/auth/consume-code` accepts `{challenge_id, code}`, with the code supplied as an eight-character decimal string. It looks up the challenge's email, then completes these atomic admissions in order before comparing any MAC:

1. IP: the existing `consume:` counter, shared with link consumption, permits 30 attempts per fixed 15-minute window. Unknown and malformed challenges still spend IP quota.
2. Email: a counter keyed by a digest of the proof's normalized email permits 10 attempts per fixed 24-hour window. Every known-challenge attempt counts, including attempts on expired, consumed or superseded proofs. Reissue and supersession never reset it; a caller-supplied email cannot choose its key.
3. Challenge: one conditional update increments attempts only on an unused, unexpired, unsuperseded iOS proof with fewer than five attempts and returns its MAC.

The Worker computes the submitted code's MAC and compares the two fixed-size MACs with Cloudflare's native constant-time `crypto.subtle.timingSafeEqual`. A matching code must then win a conditional `used_at` update that rechecks expiry and supersession. Link consumption competes for that same row: whichever wins consumes both forms. Parallel requests cannot create a second session from that proof.

Success returns `{signed_in:true}` and the existing `__Host-opax_session` cookie: host-only, `Path=/`, `Secure`, `HttpOnly`, `SameSite=Lax`, `Max-Age=2592000` (30 days). Its random token remains stored only as a SHA-256 hash. Code exchange labels the session `client:"ios"`; browser link consumption labels it `web`. The label adds no authority. Existing member lookup and logout apply to both.

Wrong, malformed, expired, superseded, consumed, unknown, disabled-account and over-limit code exchanges return the same HTTP 400 body: `{"error":"This code could not be used. Request a new sign-in email or use its link to sign in through your browser."}`. Missing or partial native schema, or a missing/short MAC secret, makes both native issuance and exchange return the existing generic HTTP 503 before spending any quota or creating a proof. Origin rejection remains the existing HTTP 403. All auth POSTs, including native issuance/exchange and cookie-bearing mutations, require the exact configured `COMMUNITY_ORIGIN`. The native core explicitly sends `Origin: https://opax.com.au` in production, and the configured staging origin when testing staging. There is no Origin bypass, CORS addition or new session header.

At the email cap, the link remains the fallback until the daily window ends. Fixed windows can allow attempts on both sides of a boundary. Carrier NAT still shares the existing IP caps. Rotating the MAC secret invalidates outstanding codes; their links remain usable unless already consumed or superseded.

## Store reviewer sign-in

The code-reviewed allowlist in `portal/src/community-auth.ts` contains only `play-review@opax.com.au` (Google Play) and `app-review@opax.com.au` (Apple). The usual trimmed, lowercase email normalization applies. These accounts can use the reusable eight-digit `REVIEWER_LOGIN_CODE` Worker secret through the existing native request and consume-code flow, without access to an inbox. The app UI and session cookie are unchanged.

Request-code for either allowlisted address sends no email and stores no one-time code or code MAC, regardless of the binding's state. It keeps the normal response and request limits; native challenge metadata still expires after 15 minutes, with the same supersession, five-attempt lockout, per-email and per-IP consume limits. Successful request responses share a 100 ms minimum time with ordinary requests; email delivery that already takes longer receives no additional delay. The reusable credential has no expiry: request a fresh challenge each sign-in. After admissions, the Worker compares it in constant time and never falls back to an emailed OTP for an allowlisted address. A successful sign-in uses normal account creation and defaults, and emits `community_reviewer_signin` with timestamp, allowlisted email and Cloudflare colo, never IP or code.

An unset, empty or malformed binding (anything other than exactly eight decimal digits) disables reviewer sign-in: both allowlisted addresses reject every code, including any previously stored emailed OTP. They never enter the stored-code path in any binding state. Other emails keep their ordinary emailed sign-in flow, with the common request response floor above.

`GET /api/ops/reviewer-login` is an operator-only, local status route (also local on staging). Its bearer guard checks the `DAILY_POST_OPERATOR_SECRET` Worker secret, the same shared guard used for daily-post engagement and run. It compares the SHA-256 digests of the presented token and the secret using the platform constant-time comparator; the Bearer header format stays exact. Missing, wrong or unconfigured operator credentials return HTTP 401. An authorized GET returns only `{"reviewer_login_enabled":true}` or `{"reviewer_login_enabled":false}`, indicating whether `REVIEWER_LOGIN_CODE` is exactly eight decimal digits; it does not inspect other auth prerequisites. All responses use `Cache-Control: no-store`. The route never returns the credential, allowlist, account details or other configuration, and never calls a provider or the production API.

An operator sets the secret interactively, with a separate value for each environment:

```sh
cd portal && npx wrangler secret put REVIEWER_LOGIN_CODE
```

For staging, use `cd portal && npx wrangler secret put REVIEWER_LOGIN_CODE --env staging`. Cloudflare secrets are write-only; keep the value in the operator's password manager, never in the repository, fixtures, logs or command arguments. Rotate it by putting a new eight-digit value with the same command and updating the relevant store's reviewer sign-in details from the password manager.

Reviewer deletion uses a fresh member-bound deletion challenge and the same `REVIEWER_LOGIN_CODE`, without sending email (local patch; release pending). It retains the existing deletion MAC, cookie, Origin, expiry and all admission limits. The current reviewer binding is checked in constant time before redemption; an unset, malformed or rotated secret invalidates old review proofs. Successful review deletion emits `community_reviewer_deletion` with timestamp and colo, never the code. Other members still receive emailed deletion codes. Deletion only mutates account database rows; it never writes secrets or vars and cannot change the constant allowlist or env binding. A later reviewer sign-in creates a fresh account with ordinary defaults and allowance.

## Sign in to connect (MCP OAuth 2.1)

Built 14 November 2026 to the MCP authorisation specification (2026-07-28). Not live until migration 0019 is applied to the production community database and the security review signs off. It is not needed for a no-sign-in directory listing.

| Address | Purpose |
| --- | --- |
| `/.well-known/oauth-protected-resource`, `…/mcp`, `…/mcp/member` | RFC 9728 resource metadata. The 401 from `/mcp` and `/mcp/member` points here in `WWW-Authenticate` (`resource_metadata`, `scope`). |
| `/.well-known/oauth-authorization-server` | RFC 8414 metadata: issuer is the site origin, `S256` only, public clients only (`none`), RFC 9207 `iss` in the response. |
| `POST /oauth/register` | RFC 7591 dynamic registration. JSON, 8 KB. 10 an hour per address, 300 for an assistant maker's shared address; 50 a day for one other network (an IPv4 address or an IPv6 /48); 2,000 a day overall, counted separately for those two groups. No secret is issued. Registrations with no connection lapse after 90 idle days. |
| `GET /oauth/authorize` | Script-free page. Signed out: a link to the email sign-in, which returns here. Signed in: explicit consent, naming the client's own claimed name and where it returns to. |
| `POST /oauth/authorize` | The decision. Needs the site's own `Origin`, the session cookie and a proof bound to that session and to the exact client, redirect address, PKCE challenge, state and resource. |
| `POST /oauth/token` | `authorization_code` (PKCE verifier required) and `refresh_token`. Form-encoded. 600 a minute per address. No limit is keyed on `client_id`: it is public, so such a limit would let anyone lock a client's members out. |
| `POST /oauth/revoke` | RFC 7009. Either token removes the whole connection. Always 200. |
| `GET /api/community/connections`, `DELETE …/connections/:id` | A signed-in member lists and removes their connected clients (shown beside API keys under Connect AI tools). |

- **Redirect addresses** match the registered string exactly. The one exception is RFC 8252 section 7.3: an `http` loopback address (`localhost`, `127.0.0.1`) may differ in its port. Registration accepts `https`, loopback `http`, and an app scheme that is either a known MCP client's (`cursor://…`, `vscode://…`) or reverse-domain (`com.example.app://…`); it refuses every other scheme, fragments, credentials, plain `http` and the site's own origin. Every fault in an authorisation request is shown on the page. OPAX redirects only after a signed-in member presses Allow or Cancel, so the address cannot be used to bounce a reader to another site. A client that returns to a program on the device (loopback or an app scheme) carries an extra warning on the consent page.
- **Clients checked** (14 November 2026): Claude `https://claude.ai/api/mcp/auth_callback`; ChatGPT `https://chatgpt.com/connector_platform_oauth_redirect` or `https://chatgpt.com/connector/oauth/{id}`; Claude Code `http://localhost:<port>/callback`; Cursor `http://localhost:8787/callback`, `https://www.cursor.com/agents/mcp/oauth/callback` and `cursor://anysphere.cursor-mcp/oauth/callback`; VS Code `http://127.0.0.1:33418` and `https://vscode.dev/redirect`. All register themselves as public clients, so no address is hard-coded.
- **Tokens:** access tokens (`opax_at_…`) last one hour; refresh tokens (`opax_rt_…`) last 60 days and rotate on every use. Authorisation codes last two minutes and work once. Only SHA-256 hashes are stored. A second use of a code or of a rotated refresh token removes the connection and every token under it; a repeat of a refresh within ten seconds is treated as a client retry and only refused. A token is accepted only if its connection was issued for this server's own `/mcp` or `/mcp/member` address (RFC 8707 audience).
- **Scope:** one, `records:read`: the public-record tools under the same session and ceiling limits as a member key, counted per connection. A connected client cannot read the member's email address, lists or messages and cannot post.
- **Client ID Metadata Documents** are not supported yet; clients fall back to dynamic registration.
- **End-to-end check:** `BASE=<origin> SESSION=<a test member's session cookie value> LIMIT=1 node portal/scripts/mcp-oauth-e2e.mjs` drives the official MCP client through the no-account tier, the 429, discovery, registration, consent, token exchange, rotation and revocation. It sends no email; make the session for a test member directly in that environment's community database. Local `wrangler dev` rewrites the `Origin` header to the production host, so the consent step only passes against a deployed Worker.
- **Account deletion** removes a member's connections, codes and tokens, and works on a database that has not had migration 0019.

## Account deletion (W5 and W6, live since 3 October 2026)

Account deletion went live in production on 3 October 2026, together with native code sign-in. It implements the defaults requested for decision 5 in [IOS-APP.md](IOS-APP.md#11-open-decisions). `/community?view=account` links to an accessible `/community?view=delete-account` flow with a fresh code field, permanent-deletion disclosure, cancel link, loading/status feedback and field errors using the shared controls.

| Method/path | JSON request | Response |
| --- | --- | --- |
| `POST /api/community/account/deletion-code` | `{}`; the server uses the signed-in member, never a submitted email or member ID | 200 `{sent:true,challenge_id,message:"Check your email for a deletion code. It expires in 15 minutes."}` |
| `POST /api/community/account/delete` | `{challenge_id,code}`; code is an eight-digit decimal **string** | 200 `{deleted:true,signed_out:true,message:"Your account and authored content have been deleted."}`; expires `__Host-opax_session` with Path=/, HttpOnly, Secure, SameSite=Lax, Max-Age=0 |

Account deletion remains reachable when `COMMUNITY_ENABLED=false` and for a disabled member with an unexpired, unrevoked cookie session. This is the orchestrator's deletion policy for App Review 5.1.1(v). Only these two routes use the deletion-specific member lookup; sign-in, other writes and moderation rules retain their existing restrictions. `GET /api/community/status` adds `can_delete_account` for a valid session, including disabled members, while its normal `member` remains NULL for disabled members. The web account entry and deletion-code UI use that boolean to keep deletion available without exposing other disabled-member features.

Both routes require the existing cookie session and an exact configured Origin, and accept at most 2,000 bytes of JSON. Missing/invalid/revoked cookie: 401; missing/wrong Origin: 403; unsupported method: 405 with Allow: POST. Code issuance/admission and verification failures use generic 400 `{"error":"This deletion could not be completed. Request a new deletion code and try again."}`. Wrong, malformed, unknown, other-member, expired, reused, superseded and over-limit proofs have the same failure body; none reveals another account or proof. Missing/partial schema, missing/short secret, email failure or database failure returns generic 503 `{"error":"This action could not be completed. Please try again shortly."}`. Responses are no-store and no-referrer. A revoked cookie’s 401 takes precedence over verification failures, including a retry after success. There is no deletion status/read endpoint, native bearer token, Origin bypass or new outbound provider call.

`community_deletion_challenges` stores a random 43-character challenge, member foreign key, MAC, attempts, creation/expiry, use/supersession and redemption marker. It reuses the native generator, secret and constant-time comparison, but uses MAC context `["opax-deletion-code-v1",member_id,challenge_id,code]`. It expires after 15 minutes and has **no sign-in link**. For ordinary accounts, sign-in links/codes cannot delete an account and deletion codes cannot sign in. The two allowlisted store reviewer accounts are the exception: they use the one `REVIEWER_LOGIN_CODE` for both, each through its own challenge. Issuance shares `login-ip:` (15/hour) and `login-email:` (5/hour); exchange spends shared `consume:` IP quota (30/15 minutes), then the known member-bound proof’s `consume-code-email:` quota (10/day), then conditionally increments its attempts (5). Malformed/unknown challenges still spend IP quota. Reissuing supersedes only deletion challenges, in the insertion batch before email delivery, and cannot reset email admission. A failed email deletes its new challenge; the older superseded challenge stays unusable, so another deletion-code request is required. This deletion-purpose rule is separate from native sign-in: native proofs supersede only after accepted delivery, leaving earlier codes and web links usable on a failed send. The response/logs contain no code.

A successful comparison must win one D1 `batch()`: conditional proof redemption rechecks expiry, supersession, member existence and the **exact cookie session hash** (including its expiry); disabled status does not remove the deletion right. A new random redemption marker guards every scope mutation. One concurrent request wins. A failing statement rolls back proof redemption and every scope change; earlier admission counters remain spent. All credentials are revoked in that transaction, the member is removed, and voice foreign keys become NULL. Sign-in session issuance also checks its still-present redeemed login proof in an atomic batch; a sign-in paused after consuming an old proof cannot recreate the account after deletion removes that proof. The guarded web statements remain compatible before 0011.

## Configuration and launch requirements

Production and staging have separate `COMMUNITY_DB` bindings. Apply every migration in `portal/migrations` to each target database before enabling accounts. Configure:

- `COMMUNITY_ORIGIN`: the exact HTTPS origin for that environment.
- `COMMUNITY_EMAIL_FROM`: an authenticated Cloudflare Email Sending address.
- `COMMUNITY_EMAIL`: the sending binding.
- `COMMUNITY_CODE_MAC_SECRET`: a new Worker secret for HMAC-SHA-256 code storage, with separate high-entropy values (at least 32 random bytes) for staging and production. The runtime requires at least 32 characters after trimming, before any native quota call. Keep it out of Wrangler vars, source and logs. Missing or short configuration refuses native issuance/exchange without spending shared web quota, storing a proof or sending email. Automated tests use a fixed test-only key.
